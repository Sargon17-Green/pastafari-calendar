# Internationalization architecture

The public PWA in this directory uses a small, dependency-free i18n layer.
Calendar calculation remains in `engine/pastafari-calendar-fast.js`; locale selection and presentation do not enter the calculation path.

## Files and loading model

- `i18n/calendar-identifiers.js` defines stable cutlet/month identifiers and the exact internal Hebrew labels currently returned by the engine.
- `i18n/locales/*.js` contains one structurally complete locale resource per registered language. Structural completeness means that the required keys are present and non-empty; it is not, by itself, a linguistic-quality certification. All 72 registered locales explicitly define the 96 `reverse.*` messages used by reverse search and the constraint editor.
- `i18n/registry.js` contains lightweight locale metadata and one dynamic `import()` loader per registered locale. Importing the registry does not import the locale resources themselves. It also resolves BCP 47 language tags, caches loaded locale modules for the lifetime of the page/module instance, formats messages, maps stable calendar indices to localized labels, and exposes explicit full-resource loading for validation.
- `i18n/runtime.js` contains browser-only locale resolution, persistence, DOM translation, and language-selector helpers.

At normal runtime, only the selected locale resource is loaded. A later language selection loads that locale on demand; a locale already loaded by the page is reused. Tests and audits that need structural validation call `loadAllLocales()` explicitly and pass the returned resources to `validateLocaleResources()`.

The worker keeps the engine's existing `cutletName` and `monthName` fields for compatibility and adds `cutletIndex` and `monthIndex`. The UI localizes only from those indices. The calculation engine itself is not localized.

## Language resolution

Priority is:

1. supported `?lang=...` URL value;
2. saved explicit selection in `localStorage` (`pastafari.language`);
3. `navigator.languages`, in browser preference order;
4. English.

A supported URL override does not overwrite the saved preference. A manual selection is loaded first, then saved and written to the current URL while preserving all other query parameters.

## Adding another locale

1. Copy one locale file in `i18n/locales/` and translate every message, calendar label, and terminology entry.
2. Add matching metadata and a dynamic loader to `LOCALES` in `i18n/registry.js`, preserving the intended selector order.
3. Add localized manifest values for the new locale.
4. Run `npm run check:reverse-i18n`, `npm test`, `npm run test:i18n-lazy`, and the browser smoke/visual checks.

Do not add optional locale files to the Service Worker's core precache. English remains in the core shell as the default fallback resource. Other locale modules are cached by the existing cache-first runtime path when they are first requested while the page is controlled by the Service Worker.

`npm run check:reverse-i18n` verifies that every registered locale contains every `reverse.*` key explicitly in its own locale source file. `validateLocaleResources()` verifies that the complete message, terminology, cutlet, and month key sets match across all 72 loaded resources and also verifies that resource metadata matches the lightweight registry metadata.

No application logic in `app.js` or `reverse-ui.js` needs a language-specific branch. Both use the same canonical `translate()` function.

## Runtime notices

The stale-current-day warning, the Kisurra-assumption notice, and the “use device location” label are ordinary per-locale message resources (`day.staleWarning`, `location.assumption`, and `location.useDevice`). All registered locales define them explicitly. `i18n/registry.js` keeps small compatibility wrapper functions for existing callers, but those wrappers delegate to the same canonical `translate()` path and contain no language-specific fallback dictionary. Full resource validation therefore covers these notices together with the rest of the shared message key set.

## PWA cache updates

The Service Worker distinguishes the core application shell from optional locale modules. The core shell is precached during installation and includes the English fallback locale. Other locale modules are not installed eagerly; after a controlled page requests one successfully, the normal cache-first fetch path stores that revisioned module URL for later reuse, including offline reuse.

Revision query strings are deployment cache keys, not API or documentation versions. Their exact current values are intentionally not duplicated here: `index.html`, the import graph, and `sw.js` are the source of truth and must remain synchronized. Whenever a cached asset changes without changing its path, the service-worker cache version must also change so an installed PWA does not keep an older byte sequence under the same cache name.

## Manifest

The manifest uses the Web App Manifest `*_localized` members for localizable name, short name, and description, with English defaults. The localized maps are kept in step with the registered runtime locales. Runtime page-language selection remains independent because manifest localization is performed by the user agent from its own localization preferences, and support for newer localization members can vary by browser version.

## Reverse-search localization

Reverse search and the multi-variable constraint editor are part of the normal site localization contract. The UI sends stable cutlet/month identifiers to `calendarLabel()` for display and converts them back to the engine's canonical internal names before solving. Changing the display locale therefore changes presentation only; it does not mutate JDN values, solver variables, constraints, an active solver snapshot, or returned solutions.
