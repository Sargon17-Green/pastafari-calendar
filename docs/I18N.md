# Internationalization architecture

The public PWA in this directory uses a small, dependency-free i18n layer.
Calendar calculation remains in `engine/pastafari-calendar-fast.js`; locale selection and presentation do not enter the calculation path.

## Files

- `i18n/calendar-identifiers.js` defines stable cutlet/month identifiers and the exact internal Hebrew labels currently returned by the engine.
- `i18n/locales/*.js` contains one structurally complete locale resource per registered language. Structural completeness means that the required keys are present and non-empty; it is not, by itself, a linguistic-quality certification.
- `i18n/registry.js` registers locales, resolves BCP 47 language tags, formats messages, maps stable calendar indices to localized labels, and validates coverage.
- `i18n/runtime.js` contains browser-only locale resolution, persistence, DOM translation, and language-selector helpers.

The worker keeps the engine's existing `cutletName` and `monthName` fields for compatibility and adds `cutletIndex` and `monthIndex`. The UI localizes only from those indices. The calculation engine itself is not localized.

## Language resolution

Priority is:

1. supported `?lang=...` URL value;
2. saved explicit selection in `localStorage` (`pastafari.language`);
3. `navigator.languages`, in browser preference order;
4. English.

A supported URL override does not overwrite the saved preference. A manual selection is saved and also written to the current URL while preserving all other query parameters.

## Adding another locale

1. Copy one locale file in `i18n/locales/` and translate every message, calendar label, and terminology entry.
2. Import that file and add it to `LOCALES` in `i18n/registry.js`.
3. Add the new locale file to the service worker asset list.
4. Add localized manifest values for the new locale.
5. Run `npm test` and the browser smoke/visual checks.

No application logic in `app.js` needs a language-specific branch.

## Runtime notices outside locale files

Three observer/day-boundary notices are currently defined in `i18n/registry.js` rather than in the per-locale resources: the stale-current-day warning, the Kisurra-assumption notice, and the “use device location” label. They have Hebrew and English forms and fall back to English for other locales. `validateLocaleResources()` therefore validates the shared per-locale key set, terminology, cutlet names, and month names, but it does not imply that these three notices are translated into every registered language.

## PWA cache updates

Revision query strings are deployment cache keys, not API or documentation versions. Their exact current values are intentionally not duplicated here: `index.html`, the import graph, and `sw.js` are the source of truth and must remain synchronized. Whenever a cached asset changes without changing its path, the service-worker cache version must also change so an installed PWA does not keep an older byte sequence under the same cache name.

## Manifest

The manifest uses the Web App Manifest `*_localized` members for localizable name, short name, and description, with English defaults. The localized maps are kept in step with the registered runtime locales; a language may still use the neutral proper name `Pastafari` as its short name. Runtime page-language selection remains independent because manifest localization is performed by the user agent from its own localization preferences, and support for newer localization members can vary by browser version.
