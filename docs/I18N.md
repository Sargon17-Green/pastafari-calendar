# Internationalization architecture

The public PWA in this directory uses a small, dependency-free i18n layer. Calendar calculation remains in `engine/pastafari-calendar-fast.js`; locale selection and presentation do not enter the calculation path.

## Files and loading model

- `i18n/calendar-identifiers.js` defines stable cutlet/month identifiers and the exact internal Hebrew labels currently returned by the engine.
- `i18n/locales/*.js` contains local language resources. The current 72 registered locale modules are structurally complete, including all 96 `reverse.*` messages and the three runtime notices. The support-level contract nevertheless permits future `partial`/`experimental` sources to omit known resources and use explicit English fallback.
- `i18n/registry.js` is the single source of truth for lightweight locale metadata, including the `complete` / `partial` / `experimental` support status. It contains one dynamic `import()` loader per registered locale, BCP 47 matching, source/result caching, fallback materialization, resource validation, provenance-aware coverage audit and formatting helpers.
- `i18n/runtime.js` contains browser-only locale resolution, persistence, DOM translation, and language-selector helpers.
- `I18N-SUPPORT-LEVELS.md` defines the support-level contract, promotion/demotion policy and coverage semantics.

Importing the registry does not eagerly import locale resources. A complete selected locale loads only itself. A partial or experimental selected locale loads itself and the English fallback baseline; local values always win. Loaded sources and resolved locales are cached for the lifetime of the page/module instance.

Tests and audits that need every original source call `loadAllLocaleSources()` and validate with `validateLocaleResources()`. Runtime callers use `loadLocale()`, which returns a complete resolved resource set. The original local source remains available internally for audit provenance so fallback cannot be mistaken for local coverage.

The worker keeps the engine's existing `cutletName` and `monthName` fields for compatibility and adds `cutletIndex` and `monthIndex`. The UI localizes only from those indices. The calculation engine itself is not localized.

## Support levels

Every registry entry has one explicit `support` value. Presence of a locale file is not a support claim.

- `complete`: every required user-facing resource is local and the locale has been explicitly approved; English fallback is forbidden for normal runtime resources.
- `partial`: meaningful local translation exists, but English fallback is permitted. A structurally complete locale can remain `partial` until linguistic review is explicit.
- `experimental`: minimal coverage is allowed, but metadata, keys, types, loading and resolved fallback output are still validated.

The compatibility property `experimental` is derived from `support`; it is not an independent source of truth. Full policy is in `I18N-SUPPORT-LEVELS.md`.

The current policy marks Hebrew and English as `complete`; the other 70 registered locales remain `partial`. All 72 current source modules nevertheless have full structural coverage, so the current coverage audit reports zero missing/fallback resource values and identifies the partial locales as structural complete-candidates rather than silently promoting them.

## Resource coverage

Validation covers:

- normal `messages`, including reverse-search, errors, accessibility labels, comparison, year-overview text, the stale-current-day warning, the Kisurra-assumption notice and the “use device location” label;
- `terminology`;
- all stable cutlet labels;
- all stable month labels;
- localized Web App Manifest name, short-name and description metadata, which remains required for every registered locale.

The runtime notices are ordinary per-locale message resources (`day.staleWarning`, `location.assumption`, and `location.useDevice`). The compatibility wrapper functions in `i18n/registry.js` delegate to the same canonical `translate()` path and contain no second language-specific dictionary.

The manifest-bound `app.title` and `meta.description` messages remain locally required so the existing manifest/runtime parity stays deterministic even for partial or experimental locales.

## Language resolution

Priority is:

1. a supported `?lang=...` URL parameter;
2. the last manually selected language stored locally;
3. `navigator.languages`, in browser preference order;
4. English.

A supported URL override does not overwrite the saved preference. A manual selection is loaded first, then saved and written to the current URL while preserving all other query parameters. Support level does not disable explicit selection.

## Validation and coverage

`npm run check:i18n` verifies registry metadata, one-to-one registry/module inventory, all locale modules and the support-level contract. Complete locales fail on any missing required resource. Partial/experimental locales may omit known resources but still fail on unknown keys, empty/non-string values, metadata mismatch or load failure.

`npm run i18n:coverage` performs the same validation, prints human-readable local/fallback coverage and writes `artifacts/i18n/coverage.json`. The JSON records per-group and overall counts, including manifest localization, missing keys, English-equality review signals and structural status suggestions.

`npm run check:reverse-i18n` remains a focused reverse-search check. It requires every `complete` locale to define all `reverse.*` messages locally, while `partial` and `experimental` locales may use the fallback allowed by their status. The general support-level validator is broader and is the authoritative check for support status.

## Adding another locale

1. Add one locale source under `i18n/locales/`.
2. Add exactly one matching registry entry with an explicit support level.
3. Add manifest localization as required by the existing PWA policy.
4. Run `npm run check:i18n`, `npm run check:reverse-i18n`, `npm test`, `npm run test:i18n-lazy`, `npm run test:i18n-support`, and the relevant browser/accessibility/visual checks.

Do not add optional locale files to the Service Worker's core precache. English remains in the core shell because it is the fallback baseline. Other locale modules are cached by the existing cache-first runtime path when first requested while the page is controlled by the Service Worker.

No application logic in `app.js` or `reverse-ui.js` needs a language-specific branch. Both use the same canonical `translate()` function.

## PWA cache updates

The Service Worker distinguishes the core application shell from optional locale modules. The core shell is precached during installation and includes the English fallback locale. Other locale modules are not installed eagerly; after a controlled page requests one successfully, the normal cache-first fetch path stores that revisioned module URL for later reuse, including offline reuse.

Revision query strings are deployment cache keys, not API or documentation versions. Their exact current values are intentionally not duplicated here: `index.html`, the import graph, and `sw.js` are the source of truth and must remain synchronized. Whenever a cached asset changes without changing its path, the service-worker cache version must also change so an installed PWA does not keep an older byte sequence under the same cache name.

## Manifest

The manifest uses the Web App Manifest `*_localized` members for localizable name, short name, and description, with English defaults. The localized maps are kept in step with the registered runtime locales. Runtime page-language selection remains independent because manifest localization is performed by the user agent from its own localization preferences, and support for newer localization members can vary by browser version.

## Reverse-search localization

Reverse search and the multi-variable constraint editor are part of the normal site localization contract. The UI sends stable cutlet/month identifiers to `calendarLabel()` for display and converts them back to the engine's canonical internal names before solving. Changing the display locale therefore changes presentation only; it does not mutate JDN values, solver variables, constraints, an active solver snapshot, or returned solutions.
