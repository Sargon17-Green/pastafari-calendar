このサイトの物語では、パスタファリ暦は「時間そのものが創造された暦」として描かれる。一方、その仕組みは厳密に定義されている。

この暦は、ある日を一つの固定された「ラベル」に変換するものではない。日付を知るには二つの日が必要だ。計算の基準となる作業日と、日付を知りたい照会日である。

作業日を c、照会日を t と書けば、日付は

F(c,t)

であって F(t) ではない。同じ照会日でも、別の作業日から計算すれば別のパスタファリ日付になりうる。

不具合ではない。そういう暦である。

パスタファリ日付を構成するもの

日付はちょうど5項目からなる。年番号、カツレツ名、カツレツ内の日番号、月名、月内の日番号である。

一般形の例なら、5000年、カツレツA、カツレツの417日目、月B、その月の83日目。

作業日、観測者の位置、日の時系列上の同一性、その他の技術情報が隣に表示されることはあるが、それらは第6の項目ではない。

なぜ作業日が必要なのか

普通の暦では、日付はその日に「属する」と考えがちだ。パスタファリ暦では、日付は二つの日の関係に依存する。

t を変えるのは別の日について尋ねることだ。c を変えるとさらに深く、年境界、カツレツ、月、その名称、月の織り合わせ方まで、問いを立てる暦の構造自体が変わりうる。

したがって今日計算した暦表が明日も正しいとは限らない。印刷した暦が丸一年も役に立ってしまう、という望ましくない事態を防げる。

同じ日でも、日付は変わる

日の同一性とパスタファリ表現は分けて考える必要がある。前者は時間軸上の安定した位置、後者は特定の作業日のもとで表示したときに得られる5項目である。

製品やAPIでは、前者を day-id と考えられる。表示方法を変えても動かない時系列上の識別子である。一方、

F(c_1,t)

と

F(c_2,t)

は同じである必要がない。

作業日を手動で変更すれば、同じ日そのものを動かさずに、その表示日付だけを変えられる。

予定、誕生、歴史的事件も同様である。出来事は安定した時系列上の同一性に固定し、パスタファリ日付は見る文脈に応じて再表示すべきだ。

ラベルは変わる。出来事は変わらない。

5000年

作業日と照会日が同じなら、

c=t

年は常に

5000

となる。つまり「今」をそれ自身から見れば、必ず5000年である。ただし5000年は固定された歴史時代ではなく、作業日に対して毎回選び直される。

作業日そのものが5000年に含まれるため、その年の別の日も5000年である。よって5000年であることは t=c の判定条件ではない。

ただし年番号は方向を示す：

Y>5000 \Rightarrow t>c

および

Y<5000 \Rightarrow t<c

0年も存在し、さらに過去へ進むと負の年番号になる。

年と門

パスタファリ年の長さは

252\text{ から }5778

日。これは実験平均ではなく、仕様上の正規の上下限である。

太陽年より短い年も、15太陽年を超える年もありうる。年境界は門の仕組みで作られ、カツレツ境界も同じ門から取られる。

年末が季節、地球の公転、月周期、あるいは「そろそろ年を終えたい」という実用上の都合に一致する必要はない。

カツレツ

各年は6〜17個のカツレツに分かれる。カツレツは時間的に連続した区間である。

今日がカツレツの250日目なら、今日が最終日でない限り明日は251日目。境界は門で、長さは最低

42

日である。

正規のカツレツ名は17個あり、一つの年の中で同じ名は繰り返されない。名称だけで長さや順序が決まることもない。

月と織り合わせ

各年には

3\text{ から }47

個の構造月があり、各月に割り当てられる日は

4\text{ から }123

日である。

ただしパスタファリの月は時間上の連続区間とは限らない。例えば時系列が

月A — 14日目
月B — 9日目
月A — 15日目

となっても正しい。月Aの15日目はその月の次の日であり、その間に別の月の日が一日入っていても構わない。

したがって「月内の日番号」は月の最初の出現から何日経ったかではなく、その年で当該月に割り当てられた何回目の日かを表す。48日目なら、その月に属する48番目の日という意味で、初出から47暦日後という意味ではない。

月どうしは互いに織り込まれる

月を一年を貫く糸だと考えるとよい。各日は必ず一つの月に属するが、明日は別の月でもよく、その後に最初の月が戻って次の番号を続けられる。

織り方には規則があり、とりわけ各月の初出・最終出現の順序には制約がある。しかし、一つの月が終わってから別の月が始まる必要はない。

  • カツレツは連続した時間区間内の位置を測る。
  • 月は消えて再登場できる構造上の糸への所属を測る。

一つの月が複数カツレツを横切ることも、一つのカツレツに多数の月が現れることもある。両者の開始・終了は一致しなくてよい。

月の「次の日」は明日とは限らない

今日がある月の17日目なら、その月の18日目はその月が次に現れる日である。明日かもしれないし、ずっと先かもしれない。

明日は次の時系列上の日、月の次の日は同じ月の次回出現を指す。

「月末」も時間的に近いとは限らない。120日ある月の119日目にいても、120日目が年のずっと後ろにあることがある。

週はない

現行の正規仕様は週の体系を定義していない。正規の7日単位も、パスタファリ曜日名も、二つの日を「同じ曜日」とする規則もない。

外部から民間の週を重ねることはできるが、それはパスタファリ日付の一部ではない。

名称

正規のカツレツ名は17個、月名は47個。一年の中で各名称はそれぞれの系統内に最大1回しか現れない。

名称の同一性は正規かつ意味論的であり、綴り、翻訳、実装の多数決で決まるものではない。名称の意味についてはヘブライ語のメギラーが最高位の典拠で、翻訳と音写は表示層である。

名称は長さの隠しコードでもない。特定のカツレツ名が長さを増やしたり、月名が短さを強制したりする規則はない。

月についての小さな事実

月名は47個、各月は最大123日なので、構文上可能な「月名＋月内日番号」は

47\times123=5781

通りある。

一年の各日はそのうち一つを実現する。年の長さを L とすれば、現れる組はちょうど L 個。しかし

L\le5778

なので、どの年にも少なくとも

5781-5778=3

個の可能な組が欠ける。最長年でも全部を使うには日数が足りない。

計算はどう行われるか

ここでは内部計算をソースと呼ぶ。中心にあるのは素数

Q=2^{127}-1

である。

処理には5個の入力カウンタ、7個の隠し滴、46個の可視滴、6個の鉢、変化する鉢順序、12回の最終攪拌、異なる答えを作る封印、組合せ選択、門生成、年選択、カツレツ分割、名称選択、月生成、月日の織り合わせが含まれる。

最終更新は同期的である。各攪拌で6個すべての新しい鉢値を同一の旧状態から計算し、その後で6個をまとめて置き換える。

12回の最終攪拌には重要な正規規則がある。旧6鉢の合計を S、攪拌番号を r とすると

R=\operatorname{SAVE}(S+149r)

を計算する。R が保存済み合計で、鉢順序の選択にも攪拌内部の更新にも、生の S ではなく R を使う。

生の合計を更新に入れていた旧版は現行の正規意味論を表さない。その旧規則から導いた例は、再検証されていない限り古いものとして扱う。

攪拌後の回答リングも、可視滴46で固定された順序を引き継ぐ。最終攪拌の順序へ自動置換してはならない。

Short Choice と Wide Choice

比較的小さい選択空間では Short Choice を使い、単純な剰余演算による偏りを避けるため棄却サンプリングを行う。

非常に大きな空間では Wide Choice を使う。ただし仕様にない性質を仮定してはいけない。

Wide Choice は、独立で一様な基数 Q の桁をインデックスが得られるまで生成する処理とは同値ではない。したがって、すべての合法な選択肢が必ず同じ正の確率を持つとは言えない。空間が十分大きければ、この選択機構から到達不能な合法候補もありうる。

暦そのものは完全に決定論的である。「Choice」はアルゴリズム段階の名称であって、利用時の抽選ではない。

誕生日と記念日

「毎年同じ日」には定義が要る。自然な構造座標として (月名, 月内日) と (カツレツ名, カツレツ内日) があり、条件を組み合わせることもできる。

したがってパスタファリの誕生日は単純な RRULE:FREQ=YEARLY ではない。選んだ再来条件を満たす次の年を検索する必要があり、元の出来事自体を自動的に「次回」と数えない。

表示のため作業日を変えても、人の同一性、出生時点、年齢を変えてはならない。

c=t となる4,096件の日付について、前後それぞれ最大250,000年にわたり、連続する各パスタファリ年を厳密に走査した結果：

  • (月名, 月内日) の再来は中央値1年。77.56%が隣接年、93.77%が2年以内、99.44%が5年以内で、観測最大は21年。
  • (カツレツ名, カツレツ内日) は中央値3年、88.89%が10年以内。ただし非常に重い裾を持ち、観測最大は51,954パスタファリ年だった。

これは調べたコーパスの経験的結果であり、すべての記念日が必ず戻るという証明でも、最大待ち時間の保証でもない。

約束をどう決めるか

パスタファリ日付だけで二人が約束するなら、少なくとも5項目の値と、それを計算した作業日を共有しなければならない。作業日は「今日」という語ではなく安定した日の識別子で保存するほうがよい。さもないと二人が別の暦を計算しうる。

  • 「明日」＝次の時系列上の日。
  • 「月の次の日」＝同じ月の次回出現。
  • 「月末」＝その月の最終出現。
  • 「一か月全部」＝月に属する日の集合、または初出から最終出現までの時系列上の全期間、のどちらもありうる。
  • 「翌年」＝選ばれた作業日のもとで構築された暦の翌年。

重要な予定なら、絶対的な時系列の日または時刻も併記してよい。暦は傷つかない。

旅行と終日予定

出来事と、その場所で表示されるラベルは別物である。時刻のある予定は安定した時点に固定すべきで、旅行しても出来事自体は時間軸上を動かない。ただし「現地の日」の定義が場所に依存するため、その瞬間に表示される現地パスタファリ日付は変わりうる。

終日予定では差がさらに大きい。民間暦の終日予定は通常、民間時の午前0時から次の午前0時まで。パスタファリの終日予定は、現地のパスタファリ日の境界から次の境界までである。通常、両者の境界時刻は一致しない。

したがってパスタファリ予定を民間暦へ無条件に「終日」として輸出すると意味が変わることがある。正確に保存するなら、時系列上のアンカーと場所・日境界の文脈を保存し、単なる all-day フラグだけにしてはいけない。

日はいつ切り替わるか

現地パスタファリ日は午前0時には変わらない。境界は金星中心のトポセントリックな下方子午線通過（現地子午線）で定める。

つまり位置依存の局地的な天文現象である。00:00である必要はなく、民間のタイムゾーンで決まらず、夏時間の開始・終了だけで移動せず、金星が肉眼で見える必要もない。

同一の物理的瞬間が、二地点ではそれぞれの現地日境界の反対側に入ることがある。利用可能な位置情報がない場合、製品はキスッラを既定の観測地点とする。

印刷暦と手計算

パスタファリ暦は印刷できる。ただし、どの作業日に対する暦かを明記する必要がある。その作業日から見た時間構造を印刷するもので、作業日が変われば新しい暦が必要になることもある。プリンターの出番はなくならない。

仕様は完全かつ決定論的なので、全部を手計算することもできる。入力カウンタを計算し、7隠し滴、46可視滴、6鉢の更新、12最終攪拌、回答生成、門構築、年・カツレツ選択、組合せ選択、名称選択、月の織り合わせを順に行えばよい。

その代わり、2月が28日だったり29日だったりすることを覚えなくて済む。

Seerとは何か

正規実装の横には高速エンジン Pastafarian Calendar Seer がある。ただしSeerは権威の源ではない。正しい日付を決めるのはメギラーと正規計算で、食い違えば誤っているのはSeerである。

目的は、同じ照会を高速に、製品へ組み込みやすい形で処理すること。

このページの編集時に行った実サービス検証では、date と now の照会、batch、日付範囲、パスタファリ日付から照会日への逆変換、年構造の取得、有効な作業日の解決、Node API、ブラウザー/HTTPクライアント、CLI、HTTP v1サービス、OpenAPI 3.1契約、ネイティブ実装と配布パッケージ、検証済みのコンテナ配備などを確認した。

したがって「Seerには公開APIがない」という古い説明は現在は誤りである。date、range、batch、year、reverse、作業日、metadata、locales、status のエンドポイントを持つ、明示的で安定したHTTP v1契約がある。

2026年9月21日にはRender上の公開HTTPS配備を実地に検証し、正確な照会、大きな範囲、再起動、cold wake、負荷時の挙動を稼働中のサービスで確認した。

ただしプロジェクト文書は、公開中のベータ／評価用配備と、SLAを備えた恒久的なホスティング済み本番サービスの宣言を区別している。原理説明ページでサーバーURL、ホスティング業者、版番号を暦の一部として固定すべきではない。

Seerは事前計算、特殊表現、SIMD、代数その他の近道を使ってよい。正規実装の計算履歴を一歩ずつ再現する必要はなく、同じ意味論的操作を行い同じ答えを返せばよい。

最適化は別の権威ではない。

起源、創設日、石板の日

ここでは正規のアンカーとサイトの物語を明確に分ける。

アンカー

固定基準日創設日は、先発グレゴリオ暦で紀元前41,222年12月22日。

創設日は「時間の始まり」ではなく計算上のアンカーである。

周辺日の番号は正の奇数・偶数で符号化する。創設日=1、その後=3, 5,…。過去方向では直前=2、その前=4、次=6,…。このカウンタでは負の番号を使わず両側を表せる。

もう一つは石板の日で、先発ユリウス暦 紀元前763年6月15日、すなわち先発グレゴリオ暦 紀元前763年6月7日。

創設日から石板の日までの正確な距離は

14{,}777{,}149

日。

どちらも時間軸上の固定アンカーだが、表示されるパスタファリ日付は照会時の作業日に依存する。

サイトの物語

サイトの編集上の語りでは、この暦は創造の一部であり、人類は十分に自覚しないまま利用し、現代に再伝達されたとされる。

これはサイトの物語であって、そのすべての叙述をメギラーの明示的な技術命題として扱ってはいけない。

再伝達の出来事自体は固定された歴史的出来事である。サイト上のパスタファリ日付は一つを永久固定するより、現在の作業日に応じて動的に表示するほうが適切だ。

上級：逆変換

作業日 c が既知なら、逆変換には非常に強い制約がある。既知のパスタファリ年内では

(\text{カツレツ名},\text{カツレツ内日})

が識別する日は最大1日。同様に

(\text{月名},\text{月内日})

も最大1日である。したがって作業日が既知なら完全な日付は照会日を一意に特定する。

5000年では距離の符号すら5項目だけでは常に決まらない。同じ完全日付が、ある文脈では作業日の過去、別の文脈では未来に現れうる。

よって完全なパスタファリ日付も、どの c で計算したか不明なら時間軸上の絶対的な位置指定にはならない。

遠い時間での構造

仕様から導いた数学研究では厳密な漸近構造も得られている。固定した作業日 c について、過去側へ十分遠く進むとアフィン周期性がある。

もし

F(c,t)=(Y,K,d_K,M,d_M)

なら、その c に対してシフト量 H_c、年変化 p_c、十分遠い閾値が存在し、閾値以降は

F(c,t-H_c)= (Y-p_c,\ K,\ d_K,\ M,\ d_M)

となる。年以外の4項目が繰り返され、年番号だけが一定量ずつ変化する。

これは固定 c の定理であり、

F(c+T,t+T)=F(c,t)

という全体的な関係を意味しない。最終的な漸近傾きが作業日ごとに本当に異なるかどうかは未解決である。

結局、パスタファリ暦とは何か

照会日だけでなく、作業日と照会日の組によって日付が決まる決定論的な暦である。

日付は必ず5項目。現在は自身から見れば常に5000年だが、その5000年自体は作業日とともに動く。年は非常に長くなりうる。カツレツは連続する。月は連続しなくてよい。正規の週はない。

月の n+1 日目は明日とは限らない。同じ時系列上の日が明日は別のパスタファリラベルを持ちうる。同じ物理的瞬間が二地点で別々の現地パスタファリ日に入ることもある。終日予定も午前0時から午前0時とは限らない。毎年の誕生日は、予定表の問題になる前に検索問題である。

それでも作業日と照会日が与えられれば曖昧さはない。正確な答えは一つだけ。

暦に必要なのは、結局それだけである。
