## 3. Root cause

### Shared invocation arena

The Dynamic01 common invocation executor already recorded an invocation-entry arena length and performed normal-return truncation, but a throw after frame reservation bypassed that cleanup. The leak therefore belonged to the generated wrapper ownership boundary, not to any individual public constructor body. Stage 4's repeated `+12` natural-failure signature and the larger injected signatures were lifecycle evidence, not constants used by the fix.

### Identity WeakMap and counter

Dynamic00 published a new object/function identity into a module-shared WeakMap and incremented the shared counter while mapping constructor arguments, before the enclosing construction had committed successfully. There was no transaction ownership record, so failed-new keys remained mapped and consumed future identity numbers.

## 4. Arena fix

The patch is placed at the Dynamic01 common invocation executor. On exceptional exit it restores the shared arena to the length captured for **that invocation's entry**, then rethrows the original exception. The existing normal-success cleanup and generated reservation/measurement ritual remain intact.

No process-startup baseline, known constant, or hard-coded `12/24/27/33` cleanup amount is used.

## 5. Why the arena fix is nesting-safe

Each wrapper owns only the state after its own saved entry point. Therefore an inner failure restores to the inner entry and leaves ancestor state intact. If the error later causes the outer invocation to fail, the outer wrapper independently restores to the outer entry. Tests at depths 1, 2, 3, 5 and 10 all returned every measured frame to its own entry state; the outer-failure scenario returned the caller-visible state to the outer invocation entry.

## 6. Identity fix

Dynamic00 now maintains a nested construction-transaction stack. A frame records the counter at entry and journals only keys that were first allocated while that frame is active. On successful nested construction, newly owned keys are transferred to the parent transaction; top-level success commits them. On failure, only that transaction's new keys are deleted and the counter is restored to its entry value when cleanup succeeds.

The fix captures `WeakMap.prototype.delete` and never enumerates the WeakMap.

## 7. Why preexisting IDs are preserved

A key that already has a mapping is never added to the rollback journal. The measured preexisting-key case retained ID `2` before and after a failing construction. Repeating failure ten times with the same previously absent key left it absent after every attempt. Three distinct failed-new keys also remained absent. Clean-history comparison produced the same allocation gap (`3 → 4`) with and without failed-new-key history.
